# OBD2 스캔하기

관리자가 차량번호로 차량 정보를 조회하고, 진단기로 차량 전체를 스캔해 위스캔 결과 형식으로 보여 줍니다. 화면은 관리자 메뉴 "진단 스캔 > 스캔하기"(`/admin/scan/`)와 대시보드의 "블루투스 진단기" 카드입니다. 웹·모바일 앱·LTE 단말기가 같은 계획과 해석을 씁니다.

순서: 시동 → 진단기 연결 → 스캔하기 → 차량번호 조회 → 차량 스캔 → 분석 결과(저장·PDF). 화면 위쪽 단계 표시(`scanner/_flow.html`)가 지금 단계와 실패 단계를 보여 줍니다.

- 블루투스 연결은 페이지마다 따로입니다. 대시보드의 "스캔하기"는 다른 화면으로 이동하지 않고 같은 카드의 연결로 스캔합니다(이동하면 연결이 끊겨 스캔할 수 없음).
- 진단기가 연결되지 않은 채 "스캔하기"를 누르면 진단기 선택 창을 띄우고 연결 단계를 실패로 표시합니다.
- 차량정보 조회 인증키가 없으면 흐름 위에 "설정 > 차량정보 조회" 안내를 보여 줍니다. 조회에 실패해도 "조회 없이 스캔 계속"으로 스캔할 수 있습니다.

## 스캔 계획 (`scanner/plan.py`)

서버가 계획(명령 단계와 조건)을 만들고, 웹(`obd-plan.js`)·앱(`obd_plan.dart`)·LTE 단말기가 같은 규칙으로 실행합니다. 진단 세션 변경(`10`)·보안 접근(`27`)·쓰기(`2E`)·루틴(`31`)은 보내지 않습니다(기본 세션에서 읽기만). 읽기 계획에는 고장코드 지우기(`04`, `14FFFFFF`)를 넣지 않습니다. `clear` 값을 보내도 무시합니다. 지우기는 아래 "고장코드 지우기"의 별도 흐름으로만 합니다(2026-10-18 대표 결정). `run_scan`은 성공한 읽기 명령만 제조사·차종당 40개까지 기억하고(`AT`·지우기·`NO DATA`·`7F`·ELM 오류 제외), 다음 계획은 그 차종 기록이 있으면 그것만, 없으면 제조사 기록을 `learned`로 붙입니다. `GET /api/scanPlan`은 같은 `build_plan`입니다. `POST /api/scans`(고장코드만)는 학습하지 않습니다. 스캔 결과는 `bms_data.wescan`에 기본 보고서(`diagnosis_info`, `vehicle`, `report`, `dtc.enhanced.ecus`, 전기차 `sensor.ev`·내연기관 `sensor.ice`)로 남깁니다. 전기·하이브리드 배터리 값은 적용 규칙과 OBDb(CC BY-SA) 정의를 그대로 읽습니다. 테슬라·아우디·BMW·렉서스는 그 OBDb 정의가 있을 때만 DID를 넣습니다.

| 묶음 | 명령 | 조건(`when`) | 내용 |
| --- | --- | --- | --- |
| 진단기 | `ATRV`, `0100`(30초), `ATDPN` | - | 전압, 통신 방식 찾기, 프로토콜 |
| 지원 PID | `0120`~`01A0` | 앞 비트맵에 그 번호 | 지원 비트맵 |
| 레디니스 | `0101`, `0141` | `0141`은 지원할 때 | 경고등, 고장코드 수, 배출 점검(가솔린·디젤) |
| 실시간 값 | `01` + PID 6개 묶음(웹·앱), PID마다 한 단계(LTE) | 지원 PID만 | 약 50개 항목 |
| 차량 정보 | `0900`, `0902`·`0904`·`0906`·`090A`·`0908`·`090B` | 모드 09 비트맵 | VIN, 보정 ID, CVN, ECU 이름, IUMPR |
| 고장코드 | `03`, `07`, `0A` | - | 확정, 대기, 영구 |
| 고장 당시 값 | `020000`, `020200`, `02xx00` | 고장코드가 있고 모드 02가 지원할 때 | 프리즈 프레임 |
| 모드 06(CAN, 웹·앱) | `0600`~`06A0`, 지원 MID마다 `06xx` | MID 비트맵 | 배출 부품 점검 결과(최소·최대 합격 판정) |
| UDS 전체 | `190209`, `190204`, `1915` | CAN만 | 기능 주소 고장코드(위카 앱과 같음) |
| UDS 제어기 | `22F190`(응답 확인), `1902FF`, `1904<DTC>FF`(최대 3개, 웹·앱), `22F187`, `22F195` | CAN만, 응답 없는 제어기는 건너뜀 | `7E0`~`7E7`, 현대·기아는 `7E4`·`7C6`·`7D1`·`7D4` 추가 |
| 현대·기아 전동차 BMS | `7E4`의 `220101`·`220105`·OBDb 셀 DID, 구형 `2101`·`2105` | CAN만 | 배터리 값, 셀 전압 |
| 실주행거리(현대·기아) | `7C6`의 `22B002`·`22B004`·`22B001`·`22B003`, 전동차는 `7E5`의 `221050` | CAN만, 계기판 `22F190`보다 먼저 | 위카 앱 dev `getClusterRange`와 같은 명령. 표준 `01A6`이 없을 때만 누적 주행거리로 씀(미검증 해석, `obd.maker_odometer`) |
| 제어기 순회(기본) | 위에서 보내지 않은 주소마다 `1902FF`(응답 확인), `1904<DTC>FF`(최대 3개) | CAN 11비트만, 응답 없으면 다음 주소. `ATST19`(≈100ms)·1초 제한 | 위카 앱 dev 목록: 공통 35쌍(`7A0`~`7A7`, `7B0`~`7B7`, `7C0`~`7C6`, `7D0`~`7D7`, `7E0`·`7E1`·`7E2`·`7E4`), 전동차·연료 미상은 32쌍 추가(`7E3`·`7E5`~`7E7`, `5E0`·`5E2`·`5A6`, `700`~`797` 일부). `717`은 `71D`로 받음. 이전에 응답한 주소를 먼저 보냄 |
| 학습 명령 | 이전에 응답한 읽기 명령 | 차종 기록, 없으면 제조사 | `learned`, 선택, 계획에 없는 것만 |
| 스캔 로직·적용 규칙 | CAN 분석에서 이 차량 범위(차종 → 제조사 → 공통)에 적용한 스캔 로직의 명령("스캔 로직: …"), 그다음 규칙의 요청(`capture_requests(car)`) | CAN만 | 계획에 없는 것만. `7DF`는 기본 주소와 같게 봄 |

- 주소: 11비트는 `ATSH7E0`+`ATCRA7E8`(응답 필터), 29비트는 `ATCP18`+`ATSH DA10F1`+`ATCRA18DAF110`. 기능 주소 요청 전에는 `ATSH7DF`(29비트 `ATCP18`+`ATSH DB33F1`)+`ATCRA`(필터 해제). 29비트 주소가 없는 제어기는 29비트 차량에서 건너뜁니다.
- 위카 앱 main 콘솔 프리셋(`ATSH7DF`~`ATSH7E8` 단독 단계, `1902FFFFFF`)은 넣지 않습니다. 단독 `ATSH`는 드라이버가 기억한 주소와 실제 주소를 어긋나게 하고 `7E8`은 응답 주소입니다. `1902FFFFFF`는 길이 오류(NRC 13)입니다.
- K-Line·J1850 차량은 CAN 전용 단계를 건너뛰고 "지원 안 함"으로 기록합니다.
- DoIP(이더넷 진단)는 ELM327 계열 진단기로 접근할 수 없어 결과에 안내만 남깁니다.
- 진단기 초기화와 오류 복구는 `docs/flows/obd.md`의 "진단기 명령"을 봅니다.

## 고장코드 지우기 (`scanner/clear.py`, 2026-10-18 대표 결정)

읽기 스캔과 따로, 저장한 스캔(지우기 전 기록)의 결과 화면에서만 시작합니다.

| 단계 | 내용 |
| --- | --- |
| 권한 | 웹: 관리자 + MFA + `users.can_clear_dtc`. 앱: 관리자·테스터 + `can_clear_dtc`(소유자는 불가) |
| 확인 | 확인 창에 차량번호·VIN·대상 제어기·고장코드 수·주의(되돌릴 수 없음, 레디니스 초기화, 고장 당시 데이터 삭제)를 보여 주고 차량번호 입력과 "정차·시동 OFF·IG ON" 체크를 받음 |
| 계획 발급 | `POST /admin/scan/<id>/clear-plan`(앱 `POST /api/scans/<id>/clearPlan`). `dtc_clear_logs`에 `issued`로 남기고 1회용 토큰(20분) 발급, 감사기록 `dtc_clear_issued` |
| 사전 점검 | `ATRV`, `010D`(차속 0이 아니면 지우지 않음), `010C` |
| 지우기 | 지우기 전 스캔(제어기 순회 포함)에서 **응답한 모든 제어기**(긍정 응답 ECU, 부정 응답 NRC·응답 대기 단계 포함, 응답 주소−8) ∪ 앱 dev 고정 6개 `7E0`·`7D2`·`7D0`·`7D6`·`7B2`·`770`에 `14FFFFFF`(3바이트 그룹). 순서는 고장코드가 나온 제어기 → 나머지 응답 제어기 → 고정 6개. 29비트 차량은 고정 6개 제외, K-Line 주소 제외. NRC 78이면 최대 6회 대기·재시도. NRC 7F(현재 세션에서 지원 안 함)면 그 제어기에만 `1003` → `14FFFFFF` → `1001` |
| 대체 | 하나라도 지우지 못했거나 OBD 고장코드가 있었으면 기능 주소 `04` |
| 다시 읽기 | 2초 뒤 `0101`, `03`, `07`, `0A`, `190209`, 대상마다 `1902FF` |
| 저장 | `POST /admin/scan/<id>/clear`(토큰 필수, 허용 명령·발급 주소만). 제어기별 결과, 04 결과, 전후 고장코드(지움·남음·새로 생김), 상태(`ok`·`partial`·`failed`·`aborted`)를 `dtc_clear_logs`에, 요약을 감사기록 `dtc_clear`에 남김 |

## 해석 (`scanner/interpret.py`, `scanner/obd.py`)

- 응답을 `# WECAR-ELM 1` 통신 기록으로 바꿔 CAN 분석 엔진(ISO-TP 결합, UDS 짝짓기, 적용 규칙)으로 해석합니다. `ATS0`(공백 없는) 응답도 읽습니다.
- 결과: 프로토콜, 전압, VIN(OBD·UDS 출처), 레디니스, 실시간 값(ECU별), 고장 당시 값, 모드 06, IUMPR, 고장코드, 제어기 목록(부품번호·소프트웨어 버전), 고장 당시 데이터(`19 04` 원값), CVN, 배터리 값·셀 전압.
- 요청 주소 `7E0`과 응답 주소 `7E8`(29비트 포함)은 같은 제어기로 묶습니다. 주 엔진 ECU는 `7E8`, 없으면 지원 PID가 가장 많은 ECU입니다.
- 고장코드는 `(5자리 코드, 제어기)`로 합치고 상태(현재·확정·대기·영구)를 모두 남깁니다. 진단 코드 DB의 설명·원인·조치를 붙입니다.
- 부정 응답: `11`·`12`·`31`·`7E`·`7F`는 "지원 안 함", `78`(응답 대기)만 받고 최종 응답이 없으면 "응답 지연"(오류로 세지 않음), 그 밖은 "부정 응답"과 사유 코드.
- PID 공식은 SAE J1979 공개 정의를 따릅니다(GPL 라이브러리 코드는 쓰지 않음).
- 배터리 값 적용 순서: CAN 분석 적용 규칙(차량 범위: 차종 → 제조사 → 공통, `active_rule_refs(car)`) → OBDb(차종 일치) → 공개 자료 기준 "참고 해석(미검증)". 표의 "근거" 열에 출처를 적습니다.

## 분석 요약 (`scanner/analysis.py`)

결과 화면과 PDF 맨 위에 보여 줍니다.

- 배출 점검(레디니스): 지원 모니터 중 완료 수와 미완료 목록(불꽃 점화·압축 점화 항목명).
- 고장코드: 개수와 상태 조합(예: 확정+영구). 모드 06은 불합격 항목만, IUMPR은 비율이 0.336보다 낮은 항목만 강조합니다.
- 전기차: SOH, 셀 전압(최고·최저·편차), 배터리 온도, 절연 저항, 누적 충방전 에너지를 값과 OBDb 정상 범위로만 보여 줍니다. 좋음·나쁨 판정은 하지 않습니다.
- 타당성 검사: OBDb 정상 범위(min·max)를 벗어난 값은 "이상값"으로 따로 보여 주고 요약 계산(셀 편차 등)에서 뺍니다. 셀 전압 합계와 팩 전압 차이(3% 초과), 최고·최저가 뒤바뀐 값, BMS 최고 셀과 셀 목록 차이(0.05 V 초과), 모듈 전압과 `ATRV` 차이(1.5 V 초과)를 경고로 표시합니다.

## 앱 스캔 (`wecar_scan`)

앱도 같은 계획으로 스캔하고 서버가 해석·저장합니다(`docs/flows/api.md`의 `GET /api/scanPlan`, `POST /api/scanRuns`).

1. 차량번호로 계획을 받아 `PlanRunner`가 실행합니다(명령 큐로 한 번에 하나, 쓰기 전 버퍼 비우기, 늦은 응답 버리기).
2. 단계 기록을 `scanRuns`로 올리면 서버가 웹과 같은 결과·PDF를 저장하고 `{id, status, errors, pdfUrl}`을 돌려줍니다.
3. 서버에 연결할 수 없으면 이전처럼 `03`·`07`·`0A`·`19 02 09`·`19 02 04`·`19 15`를 직접 읽고 CAN 수집을 올립니다.

- 고장코드는 5자리 기준으로 중복을 지우고(긴 코드 우선), B 코드는 "바디"로 분류합니다. 연료가 전기면 결과 유형을 `ev`로 보냅니다.
- 앱은 SOH를 계산하지 않습니다(서버 해석 사용).

## 오류 기록

모든 단계의 결과를 저장하고, 결과 화면의 "오류 기록"과 "전체 단계"에 보여 줍니다. 스캔이 실패해도 저장합니다.

| 상태 | 뜻 |
| --- | --- |
| 성공·지원 안 함·건너뜀 | 오류가 아님. 선택 단계의 응답 없음·부정 응답, 지원 PID에 없는 항목은 "지원 안 함" |
| 응답 없음 | `NO DATA` |
| 부정 응답 | UDS `7F` (사유 코드 표시) |
| 응답 지연 | `7F xx 78`만 받고 최종 응답이 없음. 오류로 세지 않음 |
| 시간 초과 | 진단기가 응답하지 않음 |
| 연결 끊김 | 진단기·차량 연결이 끊김(20초 안에 다시 연결되면 이어 감) |
| 단말기 오류 | `CAN ERROR`, `BUS INIT ... ERROR`, `?` 등 진단기 오류 |
| 해석 오류 | 응답을 해석하지 못함 |
| 서버 오류 | 해석 중 예외. 받은 응답은 그대로 저장 |
| 조회 실패 | 차량정보 조회 실패(인증키 없음, 한도 초과 등) |
| 화면 오류 | 브라우저에서 스캔이 중간에 멈춤. 그때까지 받은 단계는 저장 |
| PDF 오류 | 결과 PDF를 만들지 못함. 스캔은 저장되고 "PDF 내려받기"에서 다시 만듦 |
| 로직 문제 | 적용 중 스캔 로직의 명령이 성공하지 않았거나(계획에 없음 포함), 로직 수식으로 값을 읽지 못했거나 물리 범위를 벗어남. 11비트 CAN 차량에서만 점검하고, 결과 화면을 열면 팝업으로 보여 줌. 결과에 로직 버전(`scan_logic`)을 남기고, CAN 분석 "디코딩 규칙"의 문제 로그(`rule_incidents`)에도 쌓음 |

- 전체 상태: 성공(오류 없음), 일부 성공(오류 있음), 실패(OBD 응답 없음).
- 차량정보 조회 실패는 오류 기록 첫 줄에 남기고 스캔은 계속합니다.
- 결과 저장이 네트워크 문제로 실패하면 화면의 "저장 다시 시도"로 같은 결과를 다시 보냅니다.

## 결과 PDF (`scanner/pdf.py`)

- reportlab(BSD)과 나눔고딕(SIL OFL, `scanner/fonts/`)으로 A4 PDF를 만듭니다. 차량·검사 정보, 진단 요약, 고장코드, 고장 당시 값, 배터리, 실시간 값, 제어기, 오류 기록을 담습니다.
- 스캔을 저장할 때 같은 트랜잭션에서 `scan_documents`에 저장합니다(스캔당 1개). 파일 이름은 `위스캔-<차량번호>-<YYYYMMDD-HHMM>.pdf`입니다.

## 연결 방식

명령 체계(ELM327·STN·slcan)는 연결 방식과 따로 정합니다(`docs/flows/obd.md`의 "진단기 명령 체계"). 스캔 결과에는 `bms_data.dialect`와 통신 기록 머리글 `# dialect:`로 남깁니다.

| 방식 | 웹 | 앱 | 비고 |
| --- | --- | --- | --- |
| BLE | Web Bluetooth | `flutter_blue_plus` | Vlinker, OBDLink, Veepeak, Carista, WiCAN(Nordic UART) 등 이름·서비스로 찾기, "모든 기기 보기" |
| 블루투스 클래식(SPP) | Web Serial(Chrome 117 이상, 페어링 후 "블루투스 클래식·USB") | Android `flutter_classic_bluetooth` | 38400·9600·115200·500000 bps 순서로 연결 |
| USB | Web Serial | - | |
| WiFi | 지원 안 함(브라우저가 TCP 연결 불가) | 소켓 `192.168.0.10:35000` | 앱 연결 화면 WiFi 탭 |
| LTE 단말기 | - | - | 서버 API로 계획 받기·결과 올리기 (`docs/flows/telematics.md`) |
